# ADR 004: 테스트 전략

## 상태

승인됨

## 컨텍스트

코드의 품질과 안정성을 보장하기 위해 체계적인 테스트 전략이 필요합니다. 다양한 테스트 레벨과 접근 방법을 고려해야 합니다.

### 1. 단위 테스트 (Unit Tests)

**대상**:
- 각 클래스의 개별 메서드
- 비즈니스 로직 검증

**예시**:
- `ThresholdRuleTest`: 임계치 초과 감지 로직
- `RapidRiseRuleTest`: 급상승 감지 로직
- `NotificationFactoryTest`: 알림 생성 로직

**원칙**:
- 각 테스트는 하나의 시나리오만 검증
- 테스트 이름은 한국어로 작성하여 의도 명확화
- 대표 케이스만 테스트 (오버엔지니어링 방지)

### 2. 통합 테스트 (Integration Tests)

**대상**:
- 여러 컴포넌트 간의 상호작용
- 전체 플로우 검증

**예시**:
- `RulePresetsIntegrationTest`: RuleEngine + RulePresets 통합
- `FullFlowIntegrationTest`: AirQualityData → RuleEngine → Notification 전체 플로우

**원칙**:
- 실제 사용 시나리오 기반
- 여러 컴포넌트가 함께 동작하는지 검증

### 3. 테스트 프레임워크

- **Kotest**: Kotlin 친화적인 테스트 프레임워크
- **StringSpec**: 테스트 이름을 문자열로 작성하여 가독성 향상

## 고려한 대안

### 대안 1: 모든 케이스에 대해 상세 테스트

**장점**:
- 높은 테스트 커버리지
- 엣지 케이스 모두 검증

**단점**:
- 테스트 코드 유지보수 비용 증가
- 오버엔지니어링 가능성
- 테스트 실행 시간 증가

### 대안 2: 현재 선택 (대표 케이스 + 통합 테스트)

**장점**:
- 적절한 테스트 커버리지
- 테스트 유지보수 용이
- 빠른 테스트 실행

**단점**:
- 일부 엣지 케이스 누락 가능 (하지만 통합 테스트로 보완)

### 대안 3: 테스트 최소화

**장점**:
- 개발 속도 빠름

**단점**:
- 버그 발견 어려움
- 리팩토링 시 불안감
- 코드 품질 저하

## 결과

- 단위 테스트: 각 클래스의 핵심 로직 검증
- 통합 테스트: 전체 플로우 및 컴포넌트 간 상호작용 검증
- 테스트 실행 시간: 빠름 (< 5초)
- 테스트 커버리지: 주요 비즈니스 로직 커버
